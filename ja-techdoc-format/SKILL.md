書式 (ハードラップ、インライン装飾、箇条書きの粒度、ファイル分割) は `document-markdown-edit` に従う。本スキルは日本語の文体と文章構造のみを扱う。

## 語り手と読み手

- 語り手は文書自身であり、一人称は「本ドキュメント」とする。「本ページ」も可。執筆者・リポジトリオーナーを表に出さない
- 読み手を三人称で指さない。「利用者は〜する」「開発者が〜する」と書かない。読み手が行う操作は主語を省いて記述する
- 1 つの文の中で、主体を書き手側から読み手側へ移さない
  - NG: `IaC テンプレートは提供せず、AWS リソースは自前の IaC または手動で作成する`
  - OK: `IaC テンプレートは配布しない。AWS リソースの作成手段は規定しない`
- 「利用者」「ユーザー」を使ってよいのは、それが定義済みの登場人物であるとき (用語定義、図中のアクター) に限る

## 文体

である調で断定する。事実と規範を文末で区別する。

| 種別 | 文末 | 例 |
| --- | --- | --- |
| 事実 | 〜である / 〜する | `reconciler は毎サイクル 4 つのメトリクスを出力する` |
| 推奨 | 〜を推奨する / 〜すると良い | `ロググループの事前作成を推奨する` |
| 必須 | 〜すること / 〜する必要がある | `タグは初めて停止させる前に付与すること` |
| 禁止 | 〜してはいけない / 〜すべきではない | `アプリケーション層は AWS SDK に依存してはいけない` |

- 根拠は「〜ためである」で述べ、事実の文と分ける
- 修辞・比喩・口語を用いない。「飾りではない」「罠がある」「ゴミ」「何も鳴らない」「奪い合う」「〜してしまう」は不可
- 説得的な誇張を書かない。性能・費用・利点は数値または条件付きの事実として述べる

## 見出し

- 名詞句とする。動詞形・疑問形・呼びかけを用いない
  - NG: `気づく` / `中途半端に終わったときに何が残るか` / `とにかく全部起動したい` / `app は aws を import しない`
  - OK: `障害の検知` / `未完了処理の残存物` / `全リソースの一括起動` / `アプリ層から AWS アダプタへの非依存`
- 対象を掘り下げる節には「〜について」を用いてよい
- 同種の章が並ぶ場合、章内の節構成を全章で揃える

## 図表・コード例の導入

図、表、コードブロックの直前には、それが何を示すかを述べる文を必ず 1 文置く。見出しの直後にいきなり図表を置かない。

定型は次のとおりである。

| 用途 | 定型 |
| --- | --- |
| 列挙する | `〜を、以下に示す。` |
| 整理して対応づける | `〜を、以下にまとめる。` |
| 図で表す | `〜すると、次の図のようになる。` |
| 直後の内容を限定する | `〜は次のとおりである。` |

導入文は表の要約ではない。表から読み取れる内容を導入文で繰り返さない。

## 他ドキュメントの参照

- 何の詳細であるかを述べてから参照する。`詳細は、<対象> を参照。` を定型とし、文末は体言止めとする
- 参照先を名指ししない裸のリンクを置かない。リンクだけを置いて何の情報かを述べない書き方をしない
  - NG: `構成は [emulation_local.md](...)。`
  - OK: `エミュレータが再現できない API の範囲と代替手段は、[emulation_local.md](...) を参照。`
- 文中で軽く示す場合は括弧を用いてよいが、そのときも対象を名指しする
- 概要を述べる段落に参照の誘導を混ぜない。概要は概要のみを述べ、参照は該当箇所に置く

## 補足ブロック

本筋から外れる補足、背景、注意喚起は本文に混ぜず、GitHub の alert 記法へ分離する。本文は主線だけを述べる。

```markdown
> [!NOTE]
> 補足。知らなくても本文の理解と実行に支障はないが、知っていると判断が正確になる情報。

> [!TIP]
> 別解、より効率的な方法、周辺の便利な機能。

> [!IMPORTANT]
> 見落とすと目的を達成できない前提条件。

> [!WARNING]
> 従わないと不具合・データ損失・セキュリティ上の問題が生じる事項。

> [!CAUTION]
> 取り消しが困難な操作に対する警告。
```

- 種別は上記 5 つのみを用い、独自の見出しを付けない
- 1 ブロックに 1 論点とする。複数の注意を 1 ブロックへ詰めない
- 本文が成立しなくなる内容をブロックへ追い出さない。ブロックを読み飛ばしても本文は完結すること

## 記述の順序

- 定義 → 性質 → 根拠 の順に述べる
- 章の冒頭で、その章が扱う範囲を 1 段落で宣言する
- 説明の順序に理由がある場合は、順序とその理由を先に述べる
  - 例: `入力から出力への流れは A → B → C であるため、この順に説明する。`
