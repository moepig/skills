## 書式

- ハードラップはしない
- プログラミング言語の標準として定められているフォーマットが存在する場合は、その書式を使用する

## 体裁

- 関数・変数・型などの要素に対するコメントは、<要素名> は～, <要素名> is ～のような書き出しはしない。直下の要素を指すことが明らかなため

## コメント内容

### 共通

文章は以下のルールに従わねばならない。

- 科学学術論文やデータシートのように、性質を端的に記述する
  - 性質の説明は、網羅的に行う
- 性質を説明する時に、具体例を列挙した例示や、その要素の外の具体的なふるまいを関連付けた説明は、特別に必要な時を除いて行わない
  - 記述の簡潔性を維持する意図と、その要素が知るべき知識的な境界を実装だけでなくコメントでも遵守する意図
- 他のクラス、ファイル、レイヤの実装が透ける記述をしない。呼び出し先の内部処理、呼び出し元での使われ方、他レイヤの構造には触れない
  - 書いてよいのは、その要素から見えているシグネチャ、型、契約の範囲まで
  - 依存先の変更でコメントだけが実態と食い違う状態を防ぐ意図

### 通常のコード

以下を含める。

- その関数の役割を一言で表すもの
- その関数の振る舞いとそのパターン (一言で表した役割、引数、戻り値などから自明な場合は省略する)
- その要素の設計意図 (自明な場合は省略する)
- 引数の説明
- 戻り値の説明、例外の説明 (例外機構を使用する場合のみ)

### 変数・フィールドのコメント

- その変数が保持する値の役割と特性を端的に述べる。取り得る値、単位、生存期間、不変条件が特性に当たる
- その変数が実際に使われる箇所の処理を説明しない。処理の説明は、その処理の側に置く

### 実装の意図と経緯

- 個々の処理に対する意図や経緯は、関数のトップレベルのコメントに書かない。対象の処理の直前など、その処理に近い位置へインラインで書く
  - 関数のトップレベルに書けるのは、その要素そのものの設計意図に限る
- 意図や経緯を書く場合は、必ず根拠を確認してから書く。確認できないものは書かない
- 根拠が実装上の工夫に留まらず、外部の特殊な事情 (仕様の制約、既知の不具合、依存先の挙動) に基づく場合は、出典の URL と該当箇所の引用をコメントに残す

### テストコード

以下を含める。

- テストの方法
- テストが期待する結果
- その仕様の役割と意図 (自明な場合は省略する)
